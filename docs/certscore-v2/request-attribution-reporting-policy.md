# Request attribution and report grouping policy

Implemented September 17, 2026 at the product owner's request. The owner subsequently authorized release with all intended changes since the preceding deployment.

## Canonical evidence and timing

The existing observed request contract feeds normalized concerns and concern policy, then unified finding/checklist projection and report presentation. The shared promotion-grade request gate checks the canonical endpoint purpose as well as the observed classification. CMP, font delivery, security integrations, Facebook Page Plugin and supporting assets cannot establish tracking merely because a raw row calls them advertising.

`classified-request-timing.v1` retains up to twelve qualifying request/time pairs, each with a sanitized request URL, canonical vendor/product and purpose, explicit pre-consent phase, elapsed timestamp and evidence references. Policy and checklist projection use the same projector. Report rationale reads the typed packet; evidence-highlight projection applies the same gate. Generic third-party timing, vendor aggregates, text excerpts and unrelated cookies/embeds cannot supply a tracking timestamp. An established tracking finding without such proof states that its precise request timing is unavailable. Neutral or incomplete evidence must not become a gap to produce timing.

The shared vendor resolver owns endpoint product attribution. Google/Facebook host ownership alone cannot identify reCAPTCHA Enterprise or Meta Pixel. The high-risk context requires the Enterprise-specific canonical endpoint rule for the Enterprise label; generic reCAPTCHA security integration does not establish that edition or tracking. Verified Page Plugin identity remains available through the canonical registry. Raw attribution is retained as provenance where the request contract already supports it; it is not a second product assertion.

## Finding and scope presentation

Already-projected tracking and embed findings share an “Optional integrations before consent” parent. Supporting observations retain their own explanation and exact page membership. The parent's “Evidence across N pages” describes the union; it must not imply tracking on every page. Refusal-control findings remain separate. Grouping does not mutate scoring inputs, change weights, or add deductions.

The report snapshot uses “Detected integrations” and explains the difference between trackers and CMP/font/embed integrations. JSON evidence retains the constituent findings and their scopes.

## Contextual acknowledgment

`contextual-acknowledgment-description.v1` annotates a matched, retained first-layer Accept observation only when its canonical classifier retained `variant_approval_acknowledgment`. The annotation passes through normalized inventory concern and concern policy to the checklist/report. It preserves the assessment source hash, evidence references and labels, and does not change visibility counts, semantic registration, execution outcomes or scoring. “1 of 3 observed” remains valid. The report explains that acknowledgment visibility does not verify consent registration.

Refusal remediation requires a refusal/necessary-only choice, integration gating tied to that choice, and verification of runtime behavior in fresh visitor sessions. Adding a button alone is insufficient.

## Verification and cost

Regression cases cover fonts before a later tracker, fonts-only traffic, missing/post-consent timing, shared-host product over-attribution, policy-to-checklist retention, precise grouped page scope and retained acknowledgment semantics. Local browser verification covers the expanded grouping and control explanation. No production data was changed or rescanned.

No added browser run, lane, timeout, model call, infrastructure capacity or retention period. Estimated incremental bounded projection storage is below $1/month at 100,000 scans/month under existing retention, disclosed before proceeding. Deployment was subsequently authorized as part of the consolidated release.

Validation summary: 482 of 483 focused tests passed, including the canonical vendor resolver suite. The failing post-Reject rendering fixture was reproduced with the original component. A broader boundary run also identified a pre-existing GPC concern-policy fixture failure, reproduced with the original policy module. Local browser grouping/control checks and web TypeScript checks passed. Those unrelated failures were not changed as part of this work.
